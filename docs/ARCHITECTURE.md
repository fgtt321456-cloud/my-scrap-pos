# สถาปัตยกรรม RailTrack Thailand

เอกสารนี้อธิบายระบบในต้นแบบเว็บ (`railway/`) และวิธีย้ายไป Unity (`unity/`)
ต้นแบบเว็บใช้เป็นข้อกำหนดที่ทดสอบได้ ส่วน Unity ใช้ข้อมูลชุดเดียวกันผ่านไฟล์ JSON ที่ส่งออกจากเว็บ

> จัดทำเพื่อการศึกษาและพัฒนา ชื่อ ตราสัญลักษณ์ และลายรถของการรถไฟแห่งประเทศไทยยังไม่ได้รับอนุญาตให้ใช้ ต้องขออนุญาตก่อนเผยแพร่เชิงพาณิชย์

## 2. โมเดลโดเมน

**สถานี (`StationDef`)**: หน่วย 1 = 1 เมตร แกน x ตามแนวชานชาลา แกน z ขวางลาน
`kind` เป็น `T` (ปลายตัน กันชนอยู่ด้าน −x) หรือ `X` (สถานีผ่าน)
ราง (`TrackDef`) มี `cls` = ขนาดขบวนยาวที่สุดที่รับได้ (0=A ≤4 คัน, 1=B ≤6, 2=C ≤9, 3=D 10+), `siding` = รางหลีกไม่มีชานชาลา, `thru` = รางผ่าน
`locals` คือขบวนท้องถิ่นจำลองที่เสริมตารางจริง

**ขบวน (service)**: หนึ่งขบวนที่สถานีหนึ่งในวันหนึ่ง มี `mode`:
- `orig` ต้นทางที่สถานีนี้ (ออกจากศูนย์ซ่อม รับผู้โดยสาร ออก)
- `term` ปลายทาง (เข้า ส่งผู้โดยสารลง ส่งเข้าศูนย์ซ่อม)
- `thru` ผ่าน (จอดรับส่งสั้น ๆ)

วงจรสถานะ (สถานีตามตาราง):

```
sched ──(ถึงเวลา eta−5 นาที)──► approach ──(ได้ราง + คอขวดว่าง)──► entering ──► dwell ──► ready ──(ปล่อยรถ)──► departing ──► gone
                                    │ ไม่ได้ราง/คอขวดไม่ว่าง
                                    ▼
                                  held (เสียค่าปรับทุกวินาที)
```

หัวลำโพงมีวงจรละเอียดกว่า (ตั้งเส้นทาง NX, ล็อกประแจ, สับหลีกหัวรถจักร, งานกลับขบวนหลายอย่างที่ใช้ทีมร่วมกัน)
แต่ส่งข้อมูลออก UI ด้วยรูปแบบเดียวกันผ่าน adapter

**ตารางเดินรถจริง (`TimetableTrain`)**: `no, cls, line, from, to, dep, arr` จากคู่มือข้อมูลการเดินรถ
ถ้า `arr` น้อยกว่า `dep` แปลว่าถึงวันถัดไป เวลาที่ขบวนผ่านสถานีกลางทางคำนวณจากระยะทางตามรางจริง (`estimated = true`)

## 3. UI ร่วมแบบ adapter

ทุกสถานีมี adapter ชุดเดียวกัน UI ไม่อ่านสถานะการจำลองตรง ๆ:

| เมธอด | หน้าที่ |
|---|---|
| `items(filter)` | ขบวนที่จะแสดง เรียงจากเร่งด่วนที่สุด (สูงสุด 14) |
| `vm(svc)` | สร้าง `TrainViewModel` (ชื่อ, เฟส, ชานชาลา, เวลา, ปุ่มหลัก, ความล่าช้าจากต้นทาง, ขัดข้อง) |
| `platforms(svc)` | ตัวเลือกชานชาลาพร้อมเหตุผลที่ใช้ไม่ได้ ("สั้นเกินไป", "มี ...") |
| `choose(svc, n)` | จัดหรือวางแผนชานชาลา |
| `act(svc, kind)` | ปุ่มหลักของการ์ด (ปล่อยรถ / ส่งเข้าศูนย์ซ่อม) |
| `follow`, `select`, `preview` | กล้องตามขบวน, เลือก, ไฮไลต์เส้นทางระหว่างเปิดแผง |

ใน Unity ให้ทำ prefab UI ชุดเดียวที่รับ `IStationAdapter` แล้วเขียน `HuaLamphongAdapter` กับ `TimetableStationAdapter`
สองตัว เหมือน `HLP_ADAPTER`/`STN_ADAPTER` ในเว็บ

## 4. นาฬิกาโลกและการเชื่อมสถานี (`world.js`)

- **นาฬิกาโลก** `WORLD.now` (วินาทีนับจากวันที่ 0) ใช้ร่วมกันระหว่างสถานีตามตารางและแผนที่ไทย
  สถานีที่เปิดอยู่จะเลื่อนนาฬิกาไปข้างหน้า แผนที่เดินเวลาด้วย `WORLD_NET_RATE` (120 วินาทีเกมต่อ 1 วินาทีจริงที่ 1×)
- **การไล่เวลา** เมื่อกลับเข้าสถานีที่เวลาตามหลัง ทีมเวรจะจัดการทุกขบวนที่ควรออกไปแล้วให้ ผู้เล่นได้รายได้ครึ่งหนึ่ง
  ถ้าหายไปนานกว่า 2 วัน จะจำลองซ้ำเฉพาะวันสุดท้าย
- **บัญชีความล่าช้า** (`ledger`) ใช้คีย์ `เลขขบวน#วันที่เริ่มวิ่ง` เมื่อขบวนจริงออกจากสถานีของผู้เล่นช้า จะถูกบันทึกไว้
  สถานีถัดไปบนเส้นทางเดียวกันจะอ่านค่าก่อนขบวนถึง 2 ชั่วโมง และหักเวลาที่ไล่ทันระหว่างทาง (`ล่าช้า × 0.85 − 2 นาที`)
  ตัวอย่าง: ปล่อยขบวน 31 ที่กรุงเทพอภิวัฒน์ช้า 25 นาที จะไปถึงชุมทางหาดใหญ่ช้าราว 19 นาที
- **การให้คะแนน** ผู้เล่นถูกนับเฉพาะความล่าช้าที่เกิดขึ้นที่สถานีของตัวเอง ความล่าช้าที่ติดมาจากต้นทางจะไม่ถูกนับ แต่ยังส่งต่อไปสถานีถัดไป
- **แผนที่ไทย** วาดขบวนจริงทุกขบวนที่กำลังวิ่งตาม `WORLD.now` บนแนวรางจริง (สีตามสาย: เหนือ ส้ม, อีสาน น้ำเงิน, ใต้ เขียว)
  ขบวนที่ช้าเกิน 3 นาทีแสดงตัวเลขสีแดง แตะขบวนเพื่อดูเปอร์เซ็นต์ระยะทางและเวลาถึง
- **หัวลำโพงแยกนาฬิกาเอง** เพราะเดินรถธรรมดาและรถชานเมืองที่ไม่อยู่ในตารางทางไกล (ขบวนทางไกลย้ายไปกรุงเทพอภิวัฒน์แล้ว)

## 5. ความยาก (`difficulty.js` → `difficulty.json`)

| ค่า | ความหมาย | ค่าเริ่มต้น |
|---|---|---|
| `rush` | ช่วงเวลาเร่งด่วนและตัวคูณระยะห่างขบวนท้องถิ่น | 06:30–09:00 ×0.55, 16:30–19:00 ×0.6 |
| `delay` | โอกาสที่ขบวนมาช้าเมื่อไม่มีข้อมูลจากต้นทาง (+0.012 ต่อเลเวล สูงสุด 0.45) ขนาดเฉลี่ย 7 นาที สูงสุด 40 | 0.22 |
| `fault` | ขัดข้องระหว่างจอด (ประตู แอร์ เบรก เปลี่ยนกะ) ใช้เวลาเพิ่ม 4–11 นาที | 0.05 (สูงสุด 0.12) |
| `rain` | วันฝนตก (สุ่มแบบกำหนดได้ตามวัน ทุกสถานีเห็นตรงกัน): ขบวนเข้าช้าลง ×0.75, จอดนานขึ้น 2 นาที, โอกาสช้า +0.15 | 30% ของวัน |
| `ars` | ผู้ควบคุมอัตโนมัติไม่สมบูรณ์: ตอบสนองขาเข้า 20–70 วินาที, ปล่อยรถช้า 0–90 วินาที, 10% เลือกรางที่ไม่ดีที่สุด | |

ชั่วโมงแรกของหัวลำโพงไม่มีช่วงเร่งด่วน และขบวนในบทสอนจะมาตรงเวลาเสมอ

## 6. แผนการย้ายไป Unity

1. **ข้อมูล**: รัน `node railway/tools/export_unity.js` ทุกครั้งที่แก้ข้อมูลในเว็บ แล้วตรวจด้วย `sh unity/tools/check/check.sh`
   (คอมไพล์สคริปต์ทั้งหมดกับ stub ของ UnityEngine และเทียบผลกับเว็บ เช่น สภาพอากาศรายวันต้องตรงกัน)
2. **Bootstrap scene**: ใส่ `RailTrackDataLoader` + `PoolManager` รอ `RailTrackDataLoader.Ready`
3. **ระบบจำลองสถานีตามตาราง** ✅ ย้ายแล้ว: `TimetableStationSim` เป็น C# ล้วน รับ `Difficulty`, `WorldClock`, `DelayLedger`,
   `IStationHost` ผ่าน constructor ตรวจกับเว็บโดยตรง: เรขาคณิตราง 36 รางตรงกันทุกตำแหน่ง และผลการเดินรถ 24 ชม.
   ของทั้ง 5 สถานี (จำนวนขบวนออก, อัตราตรงเวลา) ใกล้เคียงกับเว็บ รวมถึงกรณีขบวน 31 ช้าจาก KRT ไป HDY
   ในฉาก: วาง `RailTrackDataLoader` + `RailTrackWorld` + `PoolManager` ใน bootstrap แล้วใส่ `TimetableStationRunner`
   (ตั้ง `stationId` และ `RollingStockCatalog`) ในฉากสถานี UI ใช้ `runner.Adapter`
4. **ฉาก**: สร้างจาก `StationDef` (รางตาม `tracks[].z`, ชานชาลาตาม `platforms[]`, อาคารตาม `style`, ของประกอบตาม `extras`)
   ตู้รถดึงจาก pool ตาม `TrainModel.id` และใช้สีจาก `livery`
5. **UI**: prefab รายการขบวน/การ์ด/แผงชานชาลาที่อ่าน `TrainViewModel` อย่างเดียว
6. **หัวลำโพง**: ย้าย `hlp_engine.js` (กราฟราง, ประแจ, NX, ล็อกเส้นทาง, ETCS, งานกลับขบวน) เป็นลำดับสุดท้าย เพราะซับซ้อนที่สุด
7. **บันทึกเกม**: `WorldClock` และ `DelayLedger` เป็น `[Serializable]` อยู่แล้ว (ledger เก็บเป็น List เพื่อให้ JsonUtility ใช้ได้)
