# การทดสอบ RailTrack

## เทสต์อัตโนมัติ (ไม่ต้องใช้มือถือ)
ดู `railway/tests/README.md`
- `smoke.test.js` ทดสอบเส้นทางเล่นหลักและการจำลองทุกสถานี
- `perf.test.js` รายงานภาระการเรนเดอร์ของแต่ละฉาก (draw call / สามเหลี่ยม / หน่วยความจำ) ซึ่งเป็นตัวเลขที่ไม่ขึ้นกับเครื่อง

ผลวัดล่าสุด (จอ 390×844, คุณภาพ eco):

| ฉาก | draw calls | triangles |
|---|---|---|
| หัวลำโพง | ~55 | ~121k |
| เชียงใหม่ | ~92 | ~56k |
| หาดใหญ่ | ~179 | ~116k |
| หนองคาย | ~83 | ~55k |
| อุบลราชธานี | ~109 | ~56k |
| กรุงเทพอภิวัฒน์ | ~157 | ~273k |

งบประมาณที่ตั้งไว้: draw call ไม่เกิน 600 และสามเหลี่ยมไม่เกิน 500k ต่อเฟรม

## ทดสอบบนมือถือจริง (ยังไม่ได้ทำ — ต้องใช้เครื่องจริง)
เปิดเกมแล้วไปที่ เมนู → ตั้งค่า → ประสิทธิภาพ → "แสดง FPS" (หรือเติม `#rtdebug` ท้าย URL) มุมล่างซ้ายจะแสดง FPS, draw call, สามเหลี่ยม, ระดับกราฟิก และ pixel ratio

| ลำดับ | สิ่งที่ทดสอบ | เกณฑ์ผ่าน |
|---|---|---|
| 1 | เปิดเกมครั้งแรกจนถึงเมนูหลัก | ไม่เกิน 5 วินาทีบน 4G |
| 2 | หัวลำโพง มุมมองทั้งสถานี 5 นาที | ≥ 30 FPS (เครื่องกลาง), ≥ 24 FPS (เครื่องเก่า) |
| 3 | กรุงเทพอภิวัฒน์ (ฉากหนักที่สุด) 5 นาที | ≥ 24 FPS และไม่ค้าง |
| 4 | สลับสถานี 10 ครั้งติดกัน | ไม่แครช, หน่วยความจำไม่โตต่อเนื่อง |
| 5 | เล่นต่อเนื่อง 30 นาที | เครื่องไม่ร้อนจนลดความเร็ว (สังเกต FPS ตก) |
| 6 | แตะ/บีบ/ลาก บนแผนที่ไทยและฉาก 3D | ตอบสนองทันที ไม่เลื่อนหน้าเว็บ |
| 7 | หมุนจอแนวนอน/แนวตั้ง | UI ไม่ซ้อนทับ, ปุ่มกดได้ |
| 8 | ปิด–เปิดแอประหว่างเล่น | เซฟกลับมาครบ |

เครื่องที่แนะนำให้ทดสอบอย่างน้อย: Android ระดับล่าง (RAM 3–4 GB), Android ระดับกลาง, iPhone รุ่นเก่า (เช่น iPhone 8/SE2), iPhone รุ่นใหม่

## ระบบช่วยเรื่องประสิทธิภาพในเกม
- เริ่มต้นที่คุณภาพ eco บนจอแคบ (มือถือ)
- ถ้า FPS ต่ำกว่า 34 ต่อเนื่อง 5 วินาทีในโหมดสูง จะลดเป็น eco อัตโนมัติ
- ถ้ายังต่ำกว่า 22 จะเข้าโหมดประหยัดสูงสุด (ปิดเงา, pixel ratio 1)
- ปิดการปรับอัตโนมัติได้ในตั้งค่า
- ข้อจำกัดที่รู้: ฉากของสถานีที่เคยเข้าไปแล้วจะยังค้างอยู่ในหน่วยความจำ (เพื่อให้สลับกลับเร็ว) ถ้ามีปัญหาหน่วยความจำบนเครื่องเล็ก ควรเพิ่มการ dispose ฉากที่ไม่ได้ใช้
